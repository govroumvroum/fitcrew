# Review guidance

- For error handling, check both nested-route and root-layout coverage, and distinguish render-time throws from rejected promises in fire-and-forget effects. (PR #59)
- Do not turn an explicitly scoped lifecycle fix into a demand for unrelated continuous/background behavior; assess whether the targeted trigger covers the reported failure window, and leave pre-existing behavior in sibling paths the diff never touches out of scope — name the boundary instead of demanding the whole area be made consistent. (PRs #56, #116)
- Comments should add project-specific reasoning rather than restate upstream documentation; a configuration entry may intentionally be inert until the referenced files exist. (PR #60)
- Audit CLI options for real callers and documented contracts; invalid user input should not silently become a default, and dead options/labels should be removed rather than preserved. (PR #64)
- Put one deadline around a bounded multi-phase async operation, including connection and completion, and clean up timers and resources on every exit path. (PR #64)
- Verify the producer's actual output contract before adding normalization for an assumed format; avoid no-op transformations. (PR #64)
- Treat eventually consistent authentication as a polling problem when appropriate; do not short-circuit on a transient negative probe merely to save a request. (PR #64)
- For read-then-write uniqueness actions, review rapid duplicate invocations and concurrent callers separately; guard in-flight UI actions, make the backend recoverable, and clean up all affected records. A cache keyed by normalized content is shared across users, so never read it with `.unique()` — one overlapping insert makes every caller throw `multiple documents`; read with `.first()` and tolerate duplicates. (PRs #67, #123)
- Review responsive layouts across the relevant viewport and UI-state matrix, including signed-in and signed-out shells; a narrow-screen check cannot validate breakpoint behavior. (PR #67)
- Every result branch in a variant/lookup flow should preserve the alternatives and version metadata needed by its consumers, not only the successful branch. (PR #66)
- Avoid duplicating repository instructions or vendored-file caveats in skills and comments; point to the durable source of truth, and record resynchronization hazards somewhere that survives the PR. (PRs #87, #78)
- For framework or component migrations, verify the installed library's actual source and rendered/interop behavior, including behavior changes and unexercised paths; do not infer the contract from names or documentation alone. (PRs #79, #81, #82)
- Treat check files as executable contracts: use a real invocation on the reviewed branch, wire permanent checks into an available command, and remove duplicate or tautological assertions. (PRs #74, #81, #82)
- Do not accept a state-machine test that merely mirrors the implementation; pin the mechanism that enforces the invariant and test route transitions, round trips, and same-state actions. (PR #83)
- For safety or validation guards, review both sides of the mutation: fail closed at every scan bound, and distinguish preventing newly written invalid data from revalidating data already stored after its governing profile changes. (PR #76)
- When moving dynamic context from an always-injected prompt to on-demand reads, preserve the old behavior and its triggers, surface truncation or missing state through the channel consumers actually read, and avoid repeating broad reads just to discard most of the result. (PR #75)
- When adding client/server arguments, use an expand/contract shape: keep new arguments optional, preserve old-client behavior, and opt into the changed behavior only where intended. (PR #91)
- Do not conflate an omitted optional field with deletion; partial patches need an explicit deletion representation, and review copy and validators against the actual persistence semantics. (PR #91)
- When adding a fallback or recovery path, trace every state branch and terminal outcome; symmetric handling in the primary branch does not prove the profile-existing, abandoned, or error branch is complete. (PR #91)
- For injected system or machine messages, preserve contracts that distinguish user-originated messages, such as first-user-message naming and user-visible history semantics. (PR #91)
- When reviewing cached prompts or tool definitions, include every provider-serialized field, especially input schemas, in the dynamic-content guard; test that the serialized prefix is stable across changing dates. (PR #90)
- Validate calendar dates by round-tripping a UTC parse to the original YYYY-MM-DD string; Date.parse alone can normalize impossible days into a different valid date. (PR #88)
- Ground tests and fixes in shapes real writers can produce; do not require metadata or behavior from a hypothetical caller with no applicable context, and make deliberate out-of-scope boundaries explicit. (PR #97)
- For SSRF guards around model- or user-controlled fetches, validate every redirect hop with bounded work, cover all address forms promised by the guard (including private IPv6), compare parsed address components rather than string prefixes, and test range boundaries. (PR #100)
- Keep a security guard's declared boundary honest: distinguish hostname checks from DNS-resolution guarantees, and do not expand a deliberately scoped hostname check into a different mechanism without evidence that scope requires it. (PR #100)
- Treat generated API artifacts as deployment-sensitive: verify generated references resolve to tracked source, and revert unrelated regeneration or shared-environment noise from the PR. (PR #100)
- Keep operation-level lifecycle indicators separate from per-part rendering progress when their UX semantics differ; a stable “still working” signal should not be driven by a transient animation hook that resets between updates. (PR #101)
- For restartable effects that track progress in refs, enumerate restart-while-running against the previous effect's stale-closure cleanup; a ref reset in the start handler loses to that cleanup, so flag the fresh start and consume it in the next effect body after cleanup. (PR #106)
- When a module claims to be the single swap point for a literal, grep for duplicate literals or parallel exports and route every consumer through it; likewise, when a value is hoisted into a single definition, sweep the file for a second expression that recomputes it and can silently diverge. (PRs #108, #114)
- Do not carry unused optional mutation arguments for a future caller; add them in the same PR that teaches the caller to send them. (PR #106)
- When deriving filesystem paths from import.meta.url in checks or scripts, decode percent-encoding via fileURLToPath rather than reading URL.pathname directly, so checks run in worktrees whose paths contain spaces or `#`. (PR #111)
- Remove dead exports with no remaining reader rather than preserving them for hypothetical consumers; sweep new modules for orphaned exports when a migration removes their only caller. (PR #111)
- Handle gone or stale resource references where empty versus gone is distinguishable (the server access layer) rather than with client query guards that cannot tell them apart; preserve fallback UX and cover stale-link paths with the same fix. (PR #111)
- Distinguish missing from not-owner in data-access guards: a gone resource may answer an empty terminated page or null, but another user's resource must still throw rather than collapsing authorization failure into missing. (PR #111)
- Before accepting a new environment/config variable, check whether the same value already has a canonical name; a second name plus a `??` fallback is a name to keep in sync with no independent reader — collapse to one name and drop the duplicate `.env.example` entry. (PR #113)
- Establish the real deploy topology before declaring a fallback dead: a build deployed off the primary platform (self-hosted) may be the only one that needs a git/commit fallback for the release tag, so removing it saves little and drops the tag for builds that do ship. (PR #114)
- Before proposing to collapse a named import into a namespace import, check the project's linter: an `import(namespace)` rule may not follow `export *` re-exports even when `tsc` resolves them, making the named import load-bearing rather than dead weight — respect an inline comment documenting that as settled and do not re-raise. (PR #115)
- The existence of a config or credential file is not proof of the value inside it: gate behavior on the credential itself, and when matching a key-value with a regex, anchor each group to its own line because `\s` matches newlines. (PR #115)
- When a per-item control (skip, stop, dismiss) mutates state that is scoped wider than the item — one session-wide timer, one active selection — verify it only touches the item's own entry; a stop fired from another row silently drops that other row's in-flight work. (PR #116)
- For end-of-flow summary screens, enumerate every terminal combination instead of keying the copy off the successful list: the all-negative case (nothing validated, everything passed) otherwise reports zero of what actually happened. (PR #116)
- When the current page holds an in-page selection (a switcher, filter, or focused card) and a CTA navigates onward, verify the link carries that selection; dropping it silently resets the destination to default order and makes the user choose again. (PR #116)
- For an error boundary added inside a card, rethrow the errors whose only remedy is a page reload (a stale client bundle calling a removed backend function) so they still reach the root error screen, and contain only errors the card can present; when the card sits in a collapsed disclosure, wrap the row so a failure renders as the same failed line instead of staying hidden behind a green summary. (PR #117)
- Once an author grounds a design choice in a validated issue's acceptance criteria or an explicit ticket requirement — a table instead of a constant, a deliberately unreachable defensive fallback — review the code against that decision and drop the alternative. (PRs #123, #117)
- Distinguish an intrinsic classification (what the item is) from its current placement before demanding a derived field follow a move; a writer that only relocates existing records does not have to rewrite it. (PR #123)
- Run safety or authorization guards over the full data set before applying a UI-driven filter: a server-side category or tab filter that runs first changes which records inherit curated attributes, so the guard's verdict depends on the open tab. (PR #123)
- A detail sheet or inspector opened from a reactive list must keep the row id and read the live row, not snapshot the object at click time, or updates landing while it is open never reach it. (PR #123)
- Check index ordering before `.take()`: take-then-sort returns the first N in index order rather than the newest N, so add an index ending in the ordering field and drop the in-memory sorts. (PR #123)
- An effect that refetches a queue which shrinks as results land will re-request items still in flight; allow one request at a time behind an in-flight guard and only re-run when the queue actually changed. (PR #123)
- For prompts or copy keyed off several independent context flags, split each sentence on the flag whose data it describes and test every combination — a combination the PR newly makes reachable otherwise points at a block that is not printed. (PR #124)
- When the diff adds a new member of an enumerated set that a shared guard or registry gates (tool cards, list entries), verify it is registered in every list controlling its rendering and that the check keeping that list honest covers it. (PR #124)
- Cut view-model fields that only restate another field and write branches an upstream guard makes unreachable; they ride through every subscription, type, and prompt with no reader. (PR #124)
